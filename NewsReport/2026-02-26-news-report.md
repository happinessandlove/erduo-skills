### 3. CLI vs MCP：懒加载策略将 AI Agent Token 消耗降低 94%

**摘要**: 作者通过对比实验指出，MCP（Model Context Protocol）在会话启动时将所有工具的完整 JSON Schema 一次性传入上下文，导致 token 消耗极高（~15,540 tokens），而 CLI 方式采用懒加载策略，仅在需要时通过 `--help` 获取单个工具详情，总体 token 消耗降低约 94%。作者据此开发了开源工具 CLIHub，可将现有 MCP Server 一键转换为 CLI 接口。

**要点**:
1. MCP 在每次会话初始化时加载全部 84 个工具的 Schema，消耗约 15,540 tokens；CLI 仅需约 300 tokens
2. CLI 懒加载机制：先列出工具名称，使用时再调用 `--help` 获取详细描述，单次工具执行仅约 910 tokens
3. Anthropic 官方的 Tool Search 功能虽也采用懒加载，但仍比 CLI 方案贵 74-88%，且仅限 Anthropic 模型

### 5. Better Reconstruction ≠ Better Generation：VAE 研究的反直觉核心发现

**摘要**: Linum 团队历时 4 个月开展 Image-Video VAE 研究，核心发现颠覆常识：针对像素级重建优化的 VAE 反而会损害下游扩散模型的生成质量。将重建 rFID 从 0.49 提升至 0.18，却导致生成 gFID 从 20.3 恶化至 45.8，原因在于过度优化会将压缩噪声引入潜空间，污染扩散模型所需的语义结构。团队还记录了多模态训练中的损失函数失衡、梯度爆炸和 Group Normalization 伪影等工程难题及解决方案。

**要点**:
1. 重建质量与生成质量存在根本性矛盾：rFID 越低不代表 gFID 越好，激进的重建优化会将数据集噪声编码进潜空间
2. 图文视频混合训练面临张量尺寸悬殊问题（视频约 8.3M vs 图像约 786K），需对损失函数做归一化加权
3. 解决路径：用自调制卷积替换 Group Norm + 自适应梯度裁剪；长期方向是用 DINO 等预训练编码器对齐 VAE 表征

**来源**: [Linum AI](https://www.linum.ai/field-notes/vae-reconstruction-vs-generation)
**关键词**: `变分自编码器` `扩散模型` `潜空间` `多模态训练` `生成质量`

### 9. 剖析 Java GC 中的 CPU 与内存关系：OpenJDK 26 新可观测性工具

**摘要**: 文章系统论证了为何仅凭 GC 暂停时长已无法衡量现代 Java 应用的计算效率：随着 G1、ZGC 等并发收集器的演进，暂停时间与实际 CPU 开销彻底解耦。作者将 GC 开销分解为显式成本（GC 线程 CPU 周期）、隐式成本（写屏障注入的应用代码）和微架构影响（缓存效应）三个维度，并介绍了 OpenJDK 26 引入的 `MemoryMXBean.getTotalGcCpuTime()` API。实证测试显示不同收集器在不同堆大小下 CPU 消耗差异可达 3.5 倍。

**要点**:
1. 暂停时间指标已过时：G1 将 79% 的 GC 工作转移至后台线程，ZGC 全部并发化，仅看 STW 时间严重低估实际 CPU 占用
2. OpenJDK 26 新工具：`MemoryMXBean.getTotalGcCpuTime()` 和 `-Xlog:cpu` 使工程师首次能直接测量 GC 占总 CPU 的百分比
3. 实测数据：xalan 下 G1 比 Parallel GC 少用 65% CPU；而 Spring 下 G1 在中等堆大小时反而多消耗 3.5 倍 CPU
